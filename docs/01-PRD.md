# WithBiz AI 제품 요구사항 정의서

작성일: 2026-10-27 · 단계: STEP 1 · 상태: 2026-10-27 사용자 계속 진행 지시에 따라 후속 단계 진행

## 1. 목적과 범위

WithBiz AI는 정부지원사업 공고를 매일 수집하고 기업 조건에 맞는 지원사업을 추천하는 반응형 웹앱이다. PC·태블릿·모바일에서 공고를 탐색하고 관심 공고를 저장하며 마감 이메일을 받을 수 있다. 설치형 PWA를 제공한다.

이 문서는 사용자가 제공한 개발구조 계획서와 개발 마스터 프롬프트를 바탕으로 작성했다. STEP 1의 요구사항만 정의하며, 외부 API 검증·설계 승인·구현 완료를 의미하지 않는다. 개발 착수일부터 12주 MVP를 목표로 하되 단계별 승인과 검증 결과에 따라 일정을 조정한다.

## 2. 사용자 페르소나

| 사용자 | 주요 문제 | 필요한 결과 |
| --- | --- | --- |
| 소상공인·중소기업 대표 | 기관별 공고를 확인할 시간이 부족하고 지원 자격을 판단하기 어렵다 | 지역과 기업 조건에 맞는 공고를 쉽게 찾고 마감을 놓치지 않는다 |
| 스타트업·중소기업 실무자 | 여러 공고의 지원내용·서류·일정을 비교해야 한다 | 검색·요약·관심 목록·캘린더로 신청 검토 시간을 줄인다 |
| 위더스컴퓨터 정보 제공·운영 담당자 | 고객에게 안내할 공고의 출처와 최신성을 확인해야 한다 | 공고를 탐색하고 수집 실패·변경 사항을 관리한다. 관리자 기능은 별도 권한 사용자만 이용한다 |

대리점 다중 고객 관리 화면과 권한 위임은 2차 범위다. 데이터 구조의 확장 가능성과 MVP 화면 제공 범위는 구분한다.

## 3. 주요 사용자 시나리오

1. 비회원이 홈에서 수집 기준일과 출처를 확인하고 유형 → 지역 → 분야를 선택한다. 목록에서 공고를 열어 요약과 원문을 확인한다.
2. 회원이 기업 프로필을 입력한다. 시스템은 재매칭 작업을 접수하고 진행 상태를 표시한다. 완료 후 추천 점수·사유·확인이 필요한 조건을 보여준다.
3. 회원이 공고를 관심 등록하고 메모를 남긴다. 캘린더에서 마감을 확인하며 동의한 설정에 따라 D-7·D-3·D-1 이메일을 받는다.
4. 공고 마감일이 변경되면 수집 과정에서 변경을 기록하고 요약·추천·알림 예약을 갱신한다. 관심 사용자에게 변경을 안내한다.
5. 관리자가 실패한 소스와 오류를 확인해 재수집을 요청한다. 실행 상태와 결과가 기록되고 공고 수정·숨김은 감사 이력에 남는다.

| F09 | 맞춤 추천 | 자격 필터 → 벡터 후보 검색 → 상위 후보 LLM 재평가를 수행한다. 점수 0~100·사유·확인 필요 조건·생성 시각·제외 사유를 표시한다 |
| F10 | 관심·캘린더 | 관심 등록·해제·메모 저장과 월·주 마감 보기를 제공한다. 중복 등록을 방지하고 미확정 마감은 별도 표시한다 |
| F11 | 알림 | 이메일 수신 설정과 D-7·D-3·D-1 선택, 주간 맞춤 요약을 제공한다. 동일 알림의 중복 발송을 방지하고 실패 이력을 남긴다 |
| F12 | 관리자 | 서버에서 관리자 역할을 확인한다. 소스별 실행 이력·실패·신규·변경 건수·수동 재수집·공고 수정·숨김·사용자 통계를 제공한다 |
| F13 | PWA | 반응형 화면과 설치 메타데이터를 제공한다. 오프라인에서는 연결 상태와 데이터 기준일을 표시하며 오래된 데이터를 최신으로 표현하지 않는다 |

카드 본문은 앱의 공고 상세로 연결하고, 원문 이동은 별도 명확한 링크로 제공하는 것을 기본안으로 한다. 원문의 카드 클릭 요구와 공고 상세 요구를 함께 충족하기 위한 가정이며 STEP 3에서 확정한다.

## 6. 기업 프로필과 AI 요구사항

프로필 항목은 사업자 유형, 기업 규모, KSIC 코드, 시도·시군구, 설립일, 매출 구간, 근로자 수, 대표자 특성, 인증, 관심 분야, 필요 지원 유형이다. 필요하지 않은 민감 항목은 수집하지 않으며 선택 항목과 매칭에 필요한 필수 항목을 STEP 3에서 확정한다.

명백한 자격 미충족만 규칙으로 제외한다. 정보 누락이나 낮은 추출 신뢰도를 미충족으로 취급하지 않는다. 기업 업력은 공고에 명시된 기준일을 우선 적용하며 기준일을 알 수 없으면 확인 필요로 남긴다. 매출 구간과 공고 한도를 확실히 비교할 수 없는 경우도 동일하게 처리한다.

AI 결과는 공고 내용 해시·모델명·프롬프트 버전과 함께 저장한다. 신규·변경 내용만 재처리하며 화면 조회는 저장된 결과를 사용한다. 기업 프로필 변경은 비동기 재매칭을 시작하고 이전 결과가 있으면 갱신 중임을 표시한다. 모델 출력은 구조 검증을 통과해야 저장한다. 공고 본문과 첨부의 지시문은 데이터로 취급한다.

모든 추천에 “최종 자격은 공고 원문으로 확인” 안내를 표시한다. AI 점수는 선정 확률을 의미하지 않는다. 추출 신뢰도 임계값과 임베딩 모델은 아직 미확정이다.

## 7. 데이터와 날짜 규칙

- 사용자 표시·업무 날짜는 Asia/Seoul 기준, 저장 시각은 시간대가 있는 값으로 관리한다.
- 이번 주는 월요일 00:00부터 다음 월요일 00:00 전까지로 가정한다. 이미 마감한 공고의 홈 노출 여부는 STEP 3에서 확정한다.
- D-day는 한국 날짜 차이로 계산한다. 종료 시각이 있으면 해당 시각을 우선한다. 날짜만 있는 경우와 상시·예산 소진 공고는 정확한 마감 시각을 임의 생성하지 않는다.
- 진행 중 지표는 접수중과 마감임박을 포함한다. 창업·기업 지표는 해당 유형의 진행 중 공고를 기본안으로 한다.
- 지역 미확인을 전국 공통으로 치환하지 않는다. 지도에서 복수 지역 공고를 집계하면 전국 고유 공고 수와 합계가 다를 수 있음을 알린다.
- 매일 상태를 다시 계산하거나 조회 시 기준일로 계산해 변경 없는 공고도 마감 상태가 갱신되어야 한다.
- 숨김 공고는 공개 조회·추천·신규 알림에서 제외한다. 기존 관심 목록의 표시는 안내 방식으로 설계한다.

## 8. 비기능 요구사항

| 영역 | 요구사항과 검증 방향 |
| --- | --- |
| 접근 제어 | 개인 데이터는 RLS로 본인만 접근한다. 다른 계정의 기업·관심·알림 접근과 일반 사용자의 관리자 접근을 테스트한다 |
| 비밀키 | 공공 API·Claude·메일·Supabase 서비스 키는 서버 환경 변수에만 둔다. 공개 번들·로그에 노출하지 않는다 |
| 입력·출력 | 입력은 Zod로 검증하고 원문·첨부 URL 및 AI 출력 형식을 검증한다. 수집한 HTML은 안전하게 처리한다 |
| 성능 | 모바일 대시보드 첫 화면 3초 이내를 목표로 한다. 기기·네트워크·표본 수·측정 지표는 STEP 3에서 고정한다 |
| 접근성 | 본문 16px 이상, WCAG AA 대비, 키보드 탐색, 폼 라벨과 오류 설명, 색 이외 상태 표시를 적용한다 |
| 신뢰성 | 한 소스의 실패가 다른 소스를 중단하지 않게 한다. 최대 3회 재시도·한도 준수·타임아웃·중복 실행 방지를 설계한다 |
| 관측 가능성 | 실패·0건·AI 오류를 기록하고 관리자에게 알린다. 로그에서 개인정보와 인증키를 제거한다 |
| 환경 분리 | 로컬·스테이징·운영 데이터와 키를 분리한다. 운영 배포는 사용자 승인 후 수행한다 |
| 복구 | 백업과 복원 절차를 문서화하고 복구 시험을 수행한다. Supabase 플랜별 백업 지원과 별도 덤프 저장소는 검증 후 확정한다 |
| 정직한 표시 | 샘플 데이터·미확인 소스·낮은 신뢰도·오래된 결과·미구현 기능을 완성된 운영 기능처럼 표시하지 않는다 |

## 9. 출시 성공 지표

| 지표 | 목표 | 측정 방법 |
| --- | --- | --- |
| 수집 연속성 | 1순위 3개 소스 30일 연속 자동 수집 | 소스별 일일 실행 이력과 실패 알림 확인. 단기 테스트로 대체하지 않는다 |
| 중복률 | 2% 이하 | 검수한 공고 집합의 중복 잔존 레코드 수 / 전체 레코드 수. 표본·판정 규칙을 기록한다 |
| 추천 품질 | 상위 10건 적합률 80% 이상 | 기업 5곳 × 공고 50건 수작업 정답표와 비교. 기업별 Precision@10 및 평균을 함께 보고한다 |
| 출처 완전성 | 공개 공고 100% | 원문 링크·출처·수집 기준일 필수값 검사 |
| 모바일 속도 | 첫 화면 3초 이내 | 합의된 모바일 환경에서 측정하고 실제 측정값 보고 |
| 알림 정확성 | 중복 발송 0건 | 동일 사용자·공고·알림 유형·기준일 재실행 테스트와 발송 이력 대조 |

추천 후보가 10개 미만이면 실제 후보 수와 적합률을 별도로 보고하며 부족한 후보를 부적격 공고로 채우지 않는다. 추천 품질과 30일 수집은 실데이터 검증 전에는 통과로 선언할 수 없다.

## 10. 기술 방향과 미검증 사항

기본 방향은 TypeScript 모노레포, Next.js App Router, Tailwind CSS, shadcn/ui, TanStack Query, Recharts, Supabase Auth·PostgreSQL·Storage·pgvector, GitHub Actions 배치, Claude, Resend, Vercel이다. 버전·요금·무료 한도·엔드포인트는 이 단계에서 검증하지 않았다.

웹앱과 collectors·normalizer·ai·matching·shared 패키지를 분리하며 jobs·supabase·tests·docs를 둔다. 실제 디렉터리 생성과 코드는 STEP 4에서 수행한다. SQL·RLS·API 명세·화면 설계는 STEP 3의 검토 대상이다.

| 프로필 | MVP는 주 기업 1개 UX, 향후 복수 기업 확장 가능한 구조를 기본안으로 한다 | STEP 3 |
| 이메일 | 일일 08:00 KST, 주간 요약 월요일 08:00 KST를 기본안으로 한다 | STEP 3 |
| 알림 변경 | 마감 연장 시 이전 예약 취소·재생성. 재알림의 중복 기준을 상세 설계한다 | STEP 3 |
| 인증 | 이메일·구글 MVP. 재설정·이메일 확인 정책과 탈퇴·보유기간 확정 필요 | STEP 3 |
| 운영 비용 | 월 사용자 1천·1만 시나리오. 호출량과 당시 요금 확인 필요 | STEP 3 |
| 기준 성능 | 시험 기기·네트워크·LCP 등 측정 기준 미확정 | STEP 3 |
| 실제 출시 | 계정·API 키·도메인·메일 인증·법률 문안·운영 승인 필요 | 해당 단계 |

비밀키는 문서나 채팅에 기록하지 않고 로컬 환경 파일 또는 각 서비스 비밀 변수에 설정한다.

## 12. 단계별 산출물과 승인

1. STEP 1: 본 PRD 검토 및 승인.
2. STEP 2: 3개 우선 소스의 실제 호출 결과, 응답 매핑, 인증·한도, 실패와 대안. 인증키 없이는 실제 검증 완료로 처리하지 않는다.
3. STEP 3: 아키텍처, ERD·스키마·RLS 설계, API 명세, 디자인 토큰·와이어프레임, 비용 추정. 설계 승인 전 구현하지 않는다.
4. STEP 4: 수집 → 목록·상세 → 대시보드 → 회원·프로필 → AI → 알림 → 관리자 순으로 구현한다.
5. STEP 5: 수집 계약·정규화·상태·추천 정답표·주요 화면 E2E 테스트 및 결과 보고.
6. STEP 6: 권한·키 노출·입력·개인정보·성능 검증과 미해결 사항 보고.
7. STEP 7: 승인된 배포, 환경 변수·설치·운영·백업·유지보수 안내.

각 단계는 결과 검토와 “다음 단계 진행” 승인 후 넘어간다. 본 문서 승인 요청은 앱 코드 구현 승인 또는 배포 승인을 대신하지 않는다.

## 13. 이번 작업 결과

- 구현 완료: STEP 1 요구사항·페르소나·시나리오·MVP 수용 조건·비기능 요구·KPI·가정 문서화. 앱 구현 코드는 작성하지 않았다.
- 테스트 완료: 제공 문서 두 개의 본문과 요구사항 대조. 실행 가능한 앱·외부 API·추천 모델 테스트는 미수행.
- 미구현·보류: STEP 2~7 전체. 단계 승인, API 접근과 디자인 확인 후 순차 진행.
